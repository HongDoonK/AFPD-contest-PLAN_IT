# customer

(라) 고객 입력 스키마. 'AI 재무설계 자동화 조립 설명서'의 공통 고객 정보(2장)와 결과 규격(9장)을 따른다. 정책 DB와 섞이지 않게 `data/customer_profiles.db`에 따로 저장한다.

```bash
python -m customer.load customer/cases/kim_doyun.json customer/cases/lee_seojun.json
```

검증에서 error가 나온 케이스는 저장하지 않는다. 저장된 케이스는 정책 판정용 값(`policy_inputs`)을 함께 출력한다.

FF(HWP·DOCX)와 원천징수영수증에서 바로 프로필을 만들려면:

```bash
python -m customer.from_documents 가상고객데이터/빈칸형_가상고객_4명/01_김민지 --case-id blank_01
```

결과는 `customer/cases/auto/`에 남고 검증을 거쳐 저장된다. 빈칸은 미확인, 어림값은 추정으로 넣는다.

## 구조

| 테이블 | 내용 |
|---|---|
| `profiles` | case_id, profile_version, 기준일, 가상 여부, 고객 유형(근로 / 사업·프리랜서 / 겸업) |
| `profile_facts` | 생년월일, 지역(코드), 거주 시작, 혼인, 가구원 수, 주택 보유, 투자성향, 병역 등 한 번만 나오는 값 |
| `income_items` | 소득원별·금액 의미별 한 행(연봉, 총급여, 근로소득금액, 지급처별 매출, 필요경비, 사업소득금액, 원천세, 세후 입금) |
| `tax_items` | 연말정산·종합소득세·사회보험 항목 |
| `assets` / `liabilities` | 잔액, 이율, 만기, 유동성, 용도 지정(세금준비금 등) |
| `cashflow_items` | 월 유출. 구역(저축·보험·세금·고정·변동), 용도(생활·업무·혼합), 빈도, 필수성, 연결 자산 |
| `insurance_contracts` | 계약자·피보험자·납입자, 보험료, 납입기간과 보장 종료를 따로 |
| `goals` | 단기·중기·장기 목표, 기한, 금액(미정이면 NULL) |
| `module_results` | 정책·소비·보험·배분 결과(9장 module_result 형식)를 버전별로 보관 |

## 규칙

- 금액은 원 단위 정수. 케이스 JSON도 원 단위로 쓴다.
- 모든 값에 `status`(기재 / 확인 / 추정 / 불일치 / 미확인 / 해당없음), `source_ref`(파일과 위치), `assumptions`를 둔다. 생략하면 값이 있으면 '기재', 없으면 '미확인'.
- 모르는 값은 `null`. 0은 0원으로 확인된 값에만 쓴다.
- 입력을 고치면 `profile_version`을 올려 새로 저장한다. 이전 버전은 남는다.

## 검증 (`validate`)

- 월 유입(`in_cashflow` 행) = 월 유출 합계
- 자산 합계 = 문서 기재 총자산, 부채 합계 = 기재 부채 (같은 돈 이중 계상 방지)
- 지급처별 매출 합계 = 총수입금액 (SNS 매출 중복 가산 방지)
- 저축 이체는 연결 자산이 있어야 함
- 정책 판정 필수 항목(생년월일, 지역 코드, 가구원 수, 주택 보유, 혼인) 누락 경고

## 정책 매칭 (`policy_match`)

```bash
python -m customer.policy_match kim_doyun
```

저장된 고객 입력과 `data/youth_policy_enriched.db`를 비교해 `output/policy_<case>_<version>.json`을 만들고, 같은 내용을 `module_results`(module='policy')에 저장한다. 형식은 조립 설명서 9장의 module_result를 따른다.

| 키 | 내용 |
|---|---|
| `search_scope` | 검색 범위와 단계별 건수(모집 중 → 지역 → 행정·홍보 제외 → 판정 → 중복 제거) |
| `summary` | 금융성 혜택 / 기타 서비스별 '입력상 충족'·'확인 필요' 수, 불충족 사유별 건수 |
| `findings` | 자금 배분에 쓰는 금융성 혜택(현금·월세·이자·보증료·대출·매칭저축·저축상품·바우처) |
| `other_findings` | 교육·상담·문화 등 그 밖의 서비스 |
| `questions` | 미확인 조건을 풀기 위한 추가 질문(많이 걸린 순) |

정책마다 `conditions`에 조건별 정책 값·고객 값·결과(충족/불충족/미확인)·근거를 남긴다. 판정 규칙:

- 연령, 취업 상태(온통청년 코드), 학력·특화 대상, 혼인, 무주택, 정책명으로 드러나는 대상 집단(신혼, 출산·양육, 군 복무, 대학생, 예술인, 농어업인, 취약계층, 창업)
- 소득은 정책 지표에 맞는 고객 값만 쓴다. 근로자는 총급여, 프리랜서는 사업소득금액을 종합소득금액 근사로 쓰고 `approximate: true`로 표시한다. 근사값이 기준선 ±10% 안이면 미확인.
- '청년 5천만원 / 청년 외 6천만원 / 신혼부부 7.5천만원'처럼 대상별 기준이 있으면 청년 기준을 쓴다.
- 원가구(부모) 기준 정책은 원가구 정보가 없으면 미확인.
- 불충족이 하나라도 있으면 제외, 미확인이 있으면 '확인 필요', 모두 충족이면 '입력상 충족'. 기관의 최종 선정이 아니며 지원금은 확정 수입으로 쓰지 않는다.

### 복지로 복지서비스 (`welfare_match.py`)

`welfare_services`(복지로 중앙부처·지자체 복지서비스)도 같은 모양으로 판정해 `findings`·`other_findings`에 함께 넣는다. 출처는 `evidence.source`('복지로 중앙부처/지자체 복지서비스'), id는 `WLF…`다.

- 대상: 생애주기에 '청년'이 있거나 이름에 '청년'이 있는 서비스. 중앙부처는 전국, 지자체는 고객 시도가 같고 시군구가 같거나 비어 있는(시도 전역) 것. 일반구가 있는 시는 시 단위로 맞춘다(41133 성남시 중원구 → 성남시).
- 온통청년 전체 정책명·자산형성 상품명과 같은 사업이면 뺀다(지역명을 떼고, 5글자 이상이면 포함 관계도 같은 사업). 온통청년에서 모집 마감·지역 때문에 빠진 사업을 되살리지 않기 위해서다.
- 복지로는 조건을 칸으로 주지 않아 문장에서 읽는다. 나이는 지원대상·선정기준의 'N~M세', 'N세 이하'(자녀 나이 같은 18세 미만 범위는 무시), 없으면 생애주기 '청년'으로 충족(`approximate`). 소득은 정책 DB와 같은 해석기로 중위소득·연소득 상한을 읽고, 원문과 가구 상황에 소득 단서가 없으면 무관으로 본다. 장애인·보훈·한부모·다문화·다자녀 가구 상황은 미확인.
- 생애주기가 넓은(청년·중장년·노년 등) 상황형 서비스(의사상자 지원, 체불임금 대지급 등)는 `situational_findings`에 따로 두고 지출 연결(`spending_handoff`)과 보고서에는 넣지 않는다. 재무 상담에서 참고용으로 쓴다.
- `search_scope.counts.welfare`에 단계별 건수(청년 대상 전체, 지역 해당, 마감, 온통청년과 같은 사업, 판정, 청년 특화/상황형)를 남긴다.

2026-11-12 기준 고객 6명에게 복지로에서 새로 들어온 서비스는 5~16건(대부분 '확인 필요')이고, 보고서의 생활비 절감 시나리오 금액은 바뀌지 않았다.

## 소비 에이전트용 요약본 (`spending_handoff`)

```bash
python -m customer.spending_handoff kim_doyun
```

정책 판정 결과(module='policy')를 소비습관 개선 에이전트가 쓰기 좋게 줄인 것. `output/spending_handoff_<case>_<version>.json`과 `module_results`(module='policy_to_spending')에 저장한다. 고객 1명당 10~17KB.

| 키 | 내용 |
|---|---|
| `totals` | 월 절감 시나리오 합계(`scenario`: 입력상 충족만, `potential`: 확인 필요 포함) |
| `expense_lines` | 고객 지출 항목마다 붙은 정책(`policy_offsets`)과 항목별 월 절감 예상 |
| `savings_programs` | 매칭저축·저축상품. 본인 저축이 필요해 지출 예산과 경쟁 |
| `one_off_income` | 지출 항목에 안 붙는 일시금(면접수당 등). 월 절감과 합산하지 않음 |
| `excluded` | 부채 수단(대출·보증료) 건수, 지출에 못 붙인 금융성 정책, 특정 집단 대상 미확인 정책 이름 |

`effect.kind`는 비율(지출 × %), 월정액, 정액할인, 일시금(월 환산 함께), 주거이전(이사해야 효과), 금액미상 중 하나다. 규칙:

- 교통비는 세부 내역의 대중교통분에만, 의료비는 의료분에만 비율을 적용한다.
- 자기개발비·문화생활비처럼 일부 지출에만 적용될 수 있으면 [0, 상한] 범위로 두고 시나리오 합계에는 하한(0)을 쓴다.
- 같은 지출 항목의 정책은 더하지 않고 가장 큰 하나만 합계에 쓴다.
- 지출이 0원인 항목, 인력양성·연구·일자리 사업, 정책명상 특정 집단 대상인데 미확인인 정책은 붙이지 않는다.

## 정책 판정용 값 (`policy_inputs`)

만 나이, 지역 코드, 가구원 수, 혼인, 주택 보유, 고객 유형과 함께, 소득을 지표별로 따로 낸다(총급여, 근로소득금액, 사업 총수입금액, 사업소득금액). 매출을 총급여로 바꿔 넣지 않는다. 가구원 수 기준 중위소득 비율도 지표마다 계산한다. 병역, 원가구 정보, 중소기업 재직, 전입일, 건강보험료처럼 판정에 필요하지만 입력에 없는 값은 `missing_fields`와 `questions`로 돌려준다.
